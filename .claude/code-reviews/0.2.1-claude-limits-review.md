## Summary

Two logical changes sit in the tree together. First, `refresh-claude` stops treating a
missing claude.ai session key as a hard failure — the statusline capture already supplies
the same windows with no credential, so the command now reports them and exits 0. Second,
the account-usage parser learned the live payload shape (`utilization`) and now refuses
windows that carry no percentage, which closes a path where a successful-looking refresh
overwrote good statusline data with windows rendering as `-`. Snapshots additionally record
which channel wrote them so the status note stops crediting the statusline for numbers the
account session fetched.

The core fixes are sound and verified against the live account (`34% / 36%`, previously
`-`). The issues below are all in the same family the change set was trying to fix:
**a snapshot's provenance and completeness are still not fully modelled.**

### Medium

**1. A partial capture silently erases the other window**

```
severity: medium
file: src/ai_coding_usage_tracker/providers/claude_limits.py
line: 87
issue: capture_windows overwrites the whole snapshot, so a payload carrying only one window drops the other
detail: The snapshot is rebuilt from scratch on every capture and written with
  _write_snapshot (line 106). A response containing five_hour but not seven_day therefore
  deletes a perfectly good weekly window rather than leaving it alone. Reproduced: capture
  both windows, then capture {"five_hour": ...} alone, and cached_quotas returns {"5h"} —
  weekly is gone from the table entirely. This is pre-existing (the overwrite predates this
  change set) but it is the same data-loss class as the clobber bug this change set fixes,
  and the new percentage requirement makes a one-sided payload slightly more reachable,
  since a percentless window is now dropped rather than kept as a resets-only entry.
suggestion: Merge per window instead of replacing wholesale — load the existing snapshot
  and carry forward any window the new payload does not supply, subject to the same MAX_AGE
  staleness check so a stale value is dropped rather than resurrected. That needs a
  per-window captured_at rather than one for the whole file.
```

**2. `captured_source` cannot see a stale snapshot, so the stale message misattributes it**

```
severity: medium
file: src/ai_coding_usage_tracker/providers/claude_limits.py
line: 285
issue: captured_source reads through load_cached (freshness-gated) while its sibling captured_age reads the file raw
detail: load_cached returns None past MAX_AGE, so captured_source falls back to
  SOURCE_STATUSLINE for any stale snapshot — including one the account session actually
  wrote. Reproduced: capture with source=SOURCE_ACCOUNT_SESSION, age the snapshot, and
  captured_source returns "statusline capture". This directly feeds cli.py:655, which
  hardcodes "last statusline capture {age} ago" in the exact branch where the snapshot is
  stale and its true source is unknowable. With a scheduled refresh running against a
  closed Claude Code, that message names the wrong channel — the same lying-note defect
  the tracker.py:139 change was made to fix.
suggestion: Give captured_source the same raw-read shape as captured_age (read the file,
  parse, return the field) so it works regardless of freshness, then use it at cli.py:655
  in place of the hardcoded "statusline capture".
```

### Low

**3. The freshness window is duplicated as a string literal**

```
severity: low
file: src/ai_coding_usage_tracker/cli.py
line: 655
issue: "past the 6h freshness limit" hardcodes a value that lives in MAX_AGE
detail: MAX_AGE = timedelta(hours=6) is the single source of truth
  (claude_limits.py:20). Changing it leaves this message asserting a number the code no
  longer uses — a small instance of the same stale-text problem finding 2 describes.
suggestion: Derive it, e.g. from int(claude_limits.MAX_AGE.total_seconds() // 3600).
```

**4. The cache file is read three times per render**

```
severity: low
file: src/ai_coding_usage_tracker/tracker.py
line: 137
issue: cached_quotas, captured_age and captured_source each independently open and parse the same JSON
detail: Same pattern at cli.py:641-644. The file is a few hundred bytes so the cost is
  irrelevant, but three parses of one file to answer three questions about one snapshot is
  a readability smell, and it lets the three answers disagree if the file changes mid-render
  (exactly what finding 2 is a symptom of).
suggestion: Load the snapshot once and derive quotas, age and source from it — either an
  accessor returning a small dataclass, or pass the loaded dict to the helpers.
```

**5. A helper that exits the process is not named like one**

```
severity: low
file: src/ai_coding_usage_tracker/cli.py
line: 632
issue: _report_limits_without_session_key raises typer.Exit(code=2) on one branch and returns on the other
detail: The caller at cli.py:706 reads as a plain reporting call, so the exit-2 path is
  invisible at the call site. It behaves correctly — this is legibility, not a bug.
suggestion: Either name the exit in the docstring summary line, or return an exit code and
  let refresh_claude raise, keeping control flow at the command level.
```

**6. Non-ASCII punctuation in terminal output**

```
severity: low
file: src/ai_coding_usage_tracker/cli.py
line: 658
issue: the new error text uses an em dash while the adjacent instructions deliberately use ASCII ("F12 -> Application")
detail: The surrounding block avoids non-ASCII (arrows written as ->), suggesting a
  deliberate choice for legacy Windows consoles. Rich handles encoding on modern terminals,
  so this is cosmetic inconsistency rather than a crash risk.
suggestion: Use " - " for consistency with the neighbouring lines.
```

### Notes (no action)

- **Exit-code change is intentional and user-visible**: `refresh-claude` returns 0 where it
  previously returned 2, whenever a fresh capture exists. Anything scripted against exit 2
  as "no key configured" would now see success. Documented in the README change; worth a
  line in the commit message.
- **Segment reorder** (`usage` before `rate_limits`, claude_limits.py:131) is correct and
  halves the request count per refresh: the live `/rate_limits` returns per-model
  concurrency tiers with no usage windows at all.
- **Test quality**: the new tests are built from the real captured payload and each asserts
  the specific defect it guards (percentless clobber, source attribution, pre-field
  snapshots). `tests/test_store.py` carries an unrelated fix for a hardcoded-date test that
  self-destructed once the wall clock passed 2026-08-18; it belongs in its own commit.
- **Commit shape**: this tree is two logical changes (UX + version bump; parsing fix +
  provenance) plus one unrelated test fix. Three commits.
